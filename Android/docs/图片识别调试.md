# 图片识别的调试手册

> 面向改 `PoemOcr` / `OcrEngine` 的人（包括以后的我）。
> 图片识别出问题，**先分清是哪一类**，再对症下药 —— 90% 的时间浪费在"没分清"上。

---

## 一、三类问题，三种查法

| 症状 | 大概率原因 | 用什么查 |
| --- | --- | --- |
| 报"没能在图里找到 6×5 的字格" | 面板检测 / 投影切格失败 | `tools\ocr_probe.py`（**不用装机**，电脑上秒出） |
| 有字格，但很多格子空着 | 逐格取字失败（装饰、极性、阈值） | `tools\ocr_one.py --dump` + `tools\montage_cell.py` |
| 格子都填满了，但字是错的 | ML Kit 本身的形近字误识 | 同上，看拼板里的字形是否完整；多跑一趟投票 / 调繁体表 |

还有一类不是识别问题：**图本身不合格**（字高 < 40px、糊成一片、字格被截断）。
用 `ocr_probe.py` 看每格墨迹占比，正常是 `0.20~0.40`，`< 0.05` 基本就是没字。

---

## 二、三个工具

### 1. `tools\ocr_probe.py` —— 只算几何，不跑 OCR

```powershell
python tools\ocr_probe.py "D:\某个难点截图.png"
python tools\ocr_probe.py "D:\难点.png" --art 0,7,14 --montage _analysis\ocr_dump\probe.png
```

它会复现 App 的整套切格逻辑（面板检测 → 暗像素投影 → **等距点阵拟合** → 每格窗口），打印：

- `面板:` / `整图 ... -> 5x6（点阵；行距 175，列距 186）` —— 走的哪条路。
  看到"均分兜底"就说明投影没切出来，这条路在本 App 里是**不可信**的兜底；
- 行带 / 列带的具体像素区间 —— 判断格子有没有错位；
- 倾斜估计 —— 拍歪的图能看出需要摆正的角度（目前不做自动摆正，只用于判断）；
- 每格 `宽×高 墨迹占比 p2/50/98 span 深浅`；
- `--art` 把指定格子打成 ASCII 点阵，肉眼核对"字有没有被切断"。

### 2. `tools\ocr_one.py` —— 在手机上真跑一张、拉回拼板

```powershell
python tools\ocr_one.py emulator-5554 "D:\难点.png" --dump
```

流程和用户点「相册识别」完全一致：广播 → 找格 → 三趟识别 → 填格 → 自动检索。
日志走 `logcat -s FhlOcr`，只打**这一次**的（脚本会等"最终 N / 30 格"出现再抓）。

`--dump` 会把三趟拼板（`montage_tight/soft/loose.png`）用 `exec-out` 二进制拉回
`_analysis\ocr_dump\`。**只有 debuggable 包能这么塞图**；装的是正式包请改用
`tools\test_ocr_gallery.py`（走系统相册通道）。

日志里值得盯的几行：

```
面板 1001x738 -> 5x6（点阵；行距 153，列距 162）      ← 切格路径
  拼板(紧) 2000x1680：24 / 30 格取到了墨迹；跳过 4,0:空  ← 哪几格没取到，为什么
  第1趟（紧）认到 24 / 30，累计 24 / 30                ← 三趟各认到多少
  第2趟（柔）认到 30 / 30，累计 30 / 30
最终 30 / 30 格
字格:                                                 ← 最终 30 格
按题库补全：气蒸云梦泽（改 1 格）                        ← 靠题库补字救回来的
```

### 3. `tools\montage_cell.py` —— 看送进 ML Kit 的到底长什么样

```powershell
python tools\montage_cell.py _analysis\ocr_dump\montage_tight.png 7,14 --size 40
```

把拼板里第 7 / 14 格打成 ASCII。常见结论：

- 字的四周还有圈/框 → 装饰没滤干净（调 `tStrong` 比例或 `dropBorderComponents`）；
- 字被切掉一截 → 窗口偏了（点阵拟合问题，退回 `ocr_probe` 查）；
- 一条细线（"一"）→ 短边补边没生效；
- 字很淡 → 该格对比度低，靠"宽"那趟兜。

## 三、可调参数在哪（`ocr/PoemOcr.kt`）

| 常量 / 位置 | 现在的值 | 作用 |
| --- | --- | --- |
| `MONTAGE_CELL` / `MONTAGE_GAP` | 240 / 80 | 拼板每格大小与格间距（送进 ML Kit 的"字号"） |
| `MAX_SIDE` | 2200 | 送进来先缩到长边 2200，再大对识别没帮助 |
| `Style` 三档的 `bboxRatio` | 0.62 / 0.44 / 0.30 | 定包围盒的阈值比例（紧 / 柔 / 宽） |
| `fitLattice` 的 `maxRes` | 0.22 | 点阵拟合的残差上限，超过就判定"不在一条等距线上" |
| `dropBorderComponents` | 触发条件 0.90 | 框住整格时，扔掉与窗口边连通的装饰框 |
| `COLS/ROWS/COUNT` | 6/5/30 | 字格规格（改了要同步 `ShiciGrid`） |
| `ShiciLogic.MIN_RESCUE_SCORE` | 8 | 按题库补救的门槛（4 个直接认对 + 1 个） |

改参数的正确姿势：**先跑 `tools\test_ocr.py` 拿 6 张样例的基线**，再改，
再跑一遍逐张对比 —— 注意"这张好了、那张坏了"是常态（例如把包围盒阈值调高，
清晰图更准，但淡字的图会开始空格子），所以看的是**总量**而不是单张。

## 五、已知局限（不是 bug，是有意的取舍）

- 形近字仍会错：`金/全`、`笑/关`、`思/息` 这类，靠形近度打分能再压一点，但代价是时间翻倍；
- 不做透视校正：拍得太斜（> 8°）就靠人重拍；
- 投票会让一张图跑 2~3 趟（约 2~4 秒），清晰图两趟一致就提前收工；
- 繁体只在**题库范围内**归简；题库外的繁体字原样保留。
